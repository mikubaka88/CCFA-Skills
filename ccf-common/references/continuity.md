# Task Continuity

Use for long tasks, material rerouting, conflicting handoffs, or recovery after lost context. Apply the small entry rule in Common to ordinary tasks without loading this whole reference. These are execution instructions and optional record checks, not detection of a provider's hidden model changes or a guarantee against capability loss.

## Goal, Route, And Action

Keep three distinct things: the current user objective and acceptance conditions; the chosen route with its evidence; and the next concrete action. The latest explicit user change updates the objective immediately. Correct a mistaken interpretation against the actual request. A question or status request normally steers the active task rather than replacing it. Preserve valid completed work.

Before a material route change, integrating a contributor's result, recovery, or final delivery, compare the affected action with the current objective, hard constraints, and acceptance conditions. Reuse the existing context or record; no per-turn recital or extra check file is needed. Explain a material mismatch or decision, not routine compliance.

Within authorized scope, correct local errors and reroute when new evidence, a verified failure, or a relevant comparison changes the decision. Record the changed assumption and consequence briefly when they matter to continuation. A fresh idea, vague self-doubt, tool outage, or older summary is not by itself a reason to replace the research goal. Tool failure calls for a tool/input repair or another supported route to the same deliverable. Contrary scientific evidence must change the affected claim or route; continuity must not preserve a disproven assumption.

Ask only for an unresolved research tradeoff or missing authorization that changes the requested scope. Complete independent work while that decision is pending. Necessary corrections and specialist prerequisites do not need renewed approval. A failed approach records its relevant conditions and result, not a permanent prohibition: retry when the input, evidence, tool, or implementation has materially changed.

## Innovation And Progress

During discovery, the stable goal may be to find a better mechanism, not to preserve the first candidate. Vary assumptions, mechanisms, or predicted behavior within that goal. A reasoned mechanism comparison or counterfactual can justify a provisional branch without already having experimental success. Label its assumptions and predictions; do not relabel them as verified observations. Strong novelty claims still need the relevant literature evidence. The extra-route preference caps optional additions, not requested brainstorming or necessary repairs.

During execution, keep the selected route unless a material assumption fails, new evidence changes the decision, a substantive limitation needs a different mechanism, or the user asks to explore. In-scope conceptual changes during authorized idea development are allowed; manuscript polishing does not authorize inventing a different method. Preserve the usable baseline while investigating an unresolved alternative, and integrate it only when its relevant comparison supports the change. Prior investment alone does not justify continuing a failed route.

Before repeating work on the same issue, identify the expected difference: a new observation/source relation, a materially different hypothesis, a concrete defect repair, or a check whose inputs changed. Paraphrasing, switching reviewer roles, rescoring unchanged evidence, and passing the same issue between skills do not count as progress. A targeted new query can be useful if it reaches missing evidence; a fixed query count is not the decision rule.

A cached read, source navigation, or repeated tool response may recover context but does not by itself add scientific evidence. Record the relevant new relation or observation when one is found; do not count requests as progress. When archiving long observations, retain their exact source/version and page, line, table, or field location for selective rereading. Keep the current goal, important negative results, unsettled alternatives, and the next discriminating action in active context. Host history replacement requires actual host support; writing a summary alone does not shrink the conversation.

If repeated attempts produce no such progress, stop that loop. Within authorized scope, choose a distinct mechanism to compare or the smallest discriminating check; otherwise deliver the supported result and name the exact unresolved decision or inaccessible input. Do not silently reduce the objective, declare success, start a compulsory experiment, or generate branches indefinitely. Necessary corrections continue when there is a concrete next fix; optional critique stops when it no longer changes the decision. Carry this reasoning across handoffs so a new owner does not reset an exhausted branch or repeat a completed check. No new per-turn log or agent call is required.

In an explicitly requested [autonomous research loop](../../ccf-pipeline-orchestrator/references/autonomous-research.md), a failed candidate ends that attempt, not the campaign. Use the remaining budget for a changed mechanism, informative replication, or justified repair. Reuse its contract, experiment records, and checkpoints for recovery instead of creating a second task-state file. Keep the best measured candidate distinct from a promising exploratory branch; an experiment crash says nothing about the scientific hypothesis until execution is repaired.

Recovery narrows the next action temporarily. Once the relevant check succeeds, resume the task's discovery or execution phase; a focused state does not suppress requested innovation. Acceptance for candidate comparison stays tied to the intended contribution and evidence, not to reaching an arbitrary reviewer score.

## Execution States

These internal states are separate from quick/standard/exploratory depth, handoff modes, and optional preferences. Do not print a state table or diagnose a degraded model by default.

| State | Trigger and action | Exit |
| --- | --- | --- |
| `normal` | Continue the scoped route; check the next material result. A small isolated error gets a local correction. | Move to focused work after a material constraint violation, repeated unchanged failure, unsupported goal replacement, or false completion. |
| `focused` | Recover the current goal and the affected evidence. Choose one bounded next step; reduce simultaneous assumptions and optional branches. Keep deliverable scope, necessary prerequisites, and evidence standards. | One relevant actual check supporting the repaired path can restore normal execution; confidence claims or a new model label cannot. |
| `reconciling` | After lost context, a handoff conflict, or a visible session/model switch, reconcile the current goal, open action, canonical artifact, and affected dependencies. Reuse a sound checkpoint; inspect only what the next decision needs. | A relevant actual check supports normal work; unresolved contradictions enter focused work. Ordinary handoffs with current evidence need no extra recovery pass. |

Do not schedule periodic self-evaluations or use universal context-length thresholds. A recorded state does not lower the requested standard or justify replacing execution with advice. If execution is genuinely blocked, state the specific dependent gap and preserve the work that can continue.

## Recover Facts Before Resuming

1. Read the current user instruction and compact active task context. When a summary is known to conflict with the task or evidence, reconstruct the facts needed for the next decision from that instruction and actual sources before comparing its conclusions with the summary. Recover required Humanization -> Common rules if missing; do not reload the whole family.
2. Separate **proposed**, **executed**, and **verified**. A plan is not an applied change; a completed tool call is not proof of a valid deliverable. Check the actual artifact and its relevant source/configuration version before trusting a previous completion statement.
3. Resolve contradictions against current primary evidence. A summary or task-state file is an index, not new evidence. Suspend the contradicted conclusion and its dependent decisions/exports; retain still-valid observations and artifacts. Carry a short correction with source anchors, not the entire unreliable rationale, into resumed work. Inspect affected decisions once against those anchors rather than re-reading or hashing every source.
4. Before repeating an operation, inspect whether its result already exists. Avoid duplicating submissions, messages, purchases, long jobs, or other side effects; existing authorization and host permissions still govern them. A resume is not authorization for a new external action.
5. Match returned contributor work to the current goal revision, source version, and edit ownership. Reuse still-valid parts of a delayed result; discard or refresh affected parts instead of applying stale edits. Serialize shared-file changes through the owner.
6. Continue from the first unresolved prerequisite or next action. Check the repaired dependency once at the relevant level. Finish when the requested artifact and applicable checks are complete.

## Domain Anchors

Preserve only the invariants that affect the current deliverable:

| Work | Anchors across a transition |
| --- | --- |
| Writing / humanization | Core problem, mechanism, supplied facts, authorized claim changes, and drafting-versus-fitting phase. Results-pending drafts remain valid; preserve intentional blanks and material negative findings. Recovery does not add defensive prose or compulsory experiments. |
| Idea / paper review | Concept-only versus manuscript scope, fixed report profile, finding IDs, source version, and rating basis. Do not import experiment-readiness criteria into concept-only review. |
| Experiments / integrity | Method configuration, evidence status, protocol, units, and actual values. A proposed run or passing parser does not become an empirical result. |
| Visuals | Data, topology, intended size, typography, alignment, and editable source. Refresh affected exports after edits; preserve the last usable artifact on failed generation. |
| Retrieval / response / submission | Source identity and anchors, dated evidence, response commitments, and exact venue/year/track where relevant. An unavailable source remains unverified. |
| Planning / maintenance | Authorized outcome, stage prerequisites, file ownership, and fixed acceptance for the current comparison. Do not declare a stage complete from the plan alone. |

## Compact Persistence

Use the active context or existing authorized report/state first. A short task creates no continuity file. For a long task that needs durable recovery, the integrating owner may maintain one optional `source/task-state.json` under its established task directory (default `ccfa-workfiles/<purpose>/<artifact-id>/`). Explicit no-new-files instructions still apply. Reuse this location across owners; no per-turn snapshots, role folders, or full reasoning transcripts.

Update at a completed stage, material route/goal change, handoff needing persistence, or recovery. Keep only the current goal, route, artifact/evidence pointers, open items, and next action; prune resolved process detail. Store concise decisions and observed outcomes, not private reasoning. An existing report can hold the same information without adopting JSON or running a checker.

This optional record does not extend or authorize writes to `ccfa.yaml`; its existing owner and schema contract remain unchanged. Personal preferences store choices, not manuscript content, task paths, or research state. Apply `artifact-contracts.md` for placement, ownership, and safe in-place replacement. When the optional build tracker uses this record, preserve its tool-managed `file_lifecycle` member while updating other fields; serialize writes and reread the current record before saving. Never edit its hashes or release status by hand, and do not create a second task state to avoid that responsibility.

### Optional JSON Record

The bundled [checker](../scripts/continuity.py) accepts this version-1 shape. References in `source` and `evidence` identify real user messages, files/sections, or checks with their relevant version; they are not proof supplied by the checker.

```json
{
  "version": 1,
  "task_id": "paper-introduction",
  "goal": {
    "revision": 1,
    "objective": "Revise the introduction from the supplied method",
    "source": "user:current-revision-request",
    "constraints": ["Preserve the method and supplied findings"],
    "acceptance": ["Complete revised introduction with supported claims"]
  },
  "route": {"id": "revise-existing", "summary": "Edit the canonical introduction"},
  "phase": "drafting",
  "mode": "normal",
  "artifacts": [
    {"path": "manuscript/introduction.tex", "revision": "working-1", "status": "executed", "evidence": []}
  ],
  "open_items": ["Check claim alignment against the supplied method"],
  "next_action": "Verify changed claims in the current introduction",
  "changes": []
}
```

`artifacts`, `open_items`, and `changes` are optional; the other shown fields are required. `goal.revision` is a positive integer. Artifact status is `proposed`, `executed`, or `verified`; verified records require evidence references. When an existing artifact's revision changes, keeping it verified requires a fresh evidence/check reference, or its status must reopen for checking. `changes` describes the latest material transition, not an accumulating log. Each entry has `kind`, `reason`, `basis`, and nonempty `evidence`; artifact retirement also has `artifact` matching the retired path.

| Change kind | Allowed basis and condition when comparing with a previous record |
| --- | --- |
| `goal` | `user_instruction` or `intent_correction`; changed objective/source/constraints/acceptance requires an increased revision. Correcting the earlier interpretation of the user's intent, including a mistaken acceptance condition against that same request, is allowed. |
| `route` | `user_instruction`, `intent_correction`, `new_evidence`, `verified_failure`, or `comparison`; give the decision-changing evidence for the new route. |
| `recovery` | `recovery_check`; moving from focused/reconciling to normal needs a relevant actual check reference. |
| `artifact_retirement` | An explicit reason and evidence under a relevant basis above; identify a previously verified artifact removed from the current record. A changed source may instead keep its path and downgrade status for revalidation. |

Reusing an identical old change entry does not establish a new transition. Anchor the current decision/check; ordinary unchanged-state updates need no new entry. Keep versioned acceptance stable within a candidate comparison. A user goal change or demonstrated evaluator error can revise it; record the reason, rerun affected comparisons under the corrected criteria, and keep old and new scores distinct. Correct an evaluator implementation without changing the goal when possible. If its stated acceptance misrepresents the unchanged user request, use `intent_correction` with evidence of that mismatch; use `user_instruction` for a newly requested standard. A candidate's poor result alone is not an evaluator error.

```bash
python ccf-common/scripts/continuity.py check path/to/task-state.json
# Validate a proposed JSON record from UTF-8 stdin against the existing canonical record:
python ccf-common/scripts/continuity.py check - --previous path/to/task-state.json
```

The command is read-only and optional. It checks types, declared evidence references, and explicit transition records; it cannot verify evidence truth, semantic goal preservation, authorization, or scientific quality. Exit 0 means recorded consistency, not task completion or model recovery. Do not add a checker invocation to every turn or maintain duplicate states just to run it.
