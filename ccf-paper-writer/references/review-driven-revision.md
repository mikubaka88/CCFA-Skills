# Review-Driven Revision

Use when applying supplied reviewer findings or requested review-based edits to manuscript text. The writer owns the revision; `ccf-paper-reviewer` owns reviewer simulation, scientific scoring, calibration and version comparison. This is not a second reviewer panel or an instruction to chase a score.

## Resolve The Actual Finding

1. Read the canonical review report or user-supplied finding and locate its affected claim/passage and evidence anchor.
2. Check that the alleged defect is present. A request for a qualifier, narrower goal or new experiment needs a factual or logical basis; an imagined objection does not justify weakening a supported argument.
3. Classify the necessary action: rewrite/reorganize/compress, clarify evidence, citation/positioning, experiment design, visual repair, reproducibility, new result, venue mismatch or an unresolved user decision.
4. Apply writing-owned fixes while preserving the authorized research, values, citations, equations and method identity. Route a material non-writing gap to its owner and integrate the returned result. Stronger prose cannot replace missing evidence.
5. Apply Humanization and the relevant [prose-quality rules](prose-quality-guardrails.md). Keep material assumptions, negative findings and mandatory disclosures in their natural scientific location; do not add generic limitations or speculative caveats to look safer.
6. Update the canonical manuscript and check the affected argument, evidence bounds, terminology, dependencies and original format once. Reopen an issue for a changed source/assumption or an actual unresolved defect, without repeating full reviews of unchanged evidence.

Close a concern when its actual defect is resolved, even if a score has not changed. A requested score target does not authorize endless wording changes or unsupported claims. Complete supported revisions and identify the specific remaining dependency when progress needs new evidence or a research decision. Continue independent work without creating a warning artifact by default.

## Scores And Revision Records

Read linked reviewer scorecards when relevant; do not recompute, combine or promise movement in them. The reviewer's frozen historical/current progress comparison and absolute venue-readiness scorecard remain separate. Request re-evaluation only when a new review/score is within the user's scope.

Return the revised artifact first. If the user needs an action table, reuse its existing issue IDs and record the affected location, basis, writing action, external owner if needed, and status (`applied`, `needs evidence`, `needs user decision`). Do not make a report or critique file per pass. Formal historical/current score deltas and the canonical response ledger remain with the reviewer/rebuttal owner; preserve the user's source format and update files in place.
